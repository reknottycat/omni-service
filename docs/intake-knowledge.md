# 会话知识文档与本体规划

每个客服会话生成一份知识文档。用现有 `conversations.id` 作为稳定文档 ID，会话建立时创建草稿，后续轮次和人工校对追加修订。AI 关闭时，人工会话也走同一流程。结构化数据作为主记录，供员工阅读的文档由同一记录渲染。[会话与消息持久化](../src/omni_service/store.py)

## 实体与关系

| 实体 | 内容与关系 |
|---|---|
| `Conversation` 会话 | 记录渠道、会话 ID、语言、交接状态、有序消息和当前文档版本。一个会话可以关联多条运输需求。 |
| `Organization` 客户公司 | `requests` 一条或多条 `ShipmentIntent`。客户未说明公司时保留空值。跨会话或跨渠道合并公司需人工确认。 |
| `ShipmentIntent` 运输需求 | `hasCargo` 一条或多条 `CargoLine`，通过 `hasRoute` 关联 `Route`。首期从会话整理一条需求，多批货由人工拆分。 |
| `CargoLine` 货物 | 品类及需求数量，保留单位、范围等原始措辞。可审核后另存规范单位。 |
| `Route` 路线 | 分别关联起点 `origin` 和终点 `destination`。存在同名地点时，待人工核实后再关联标准地点条目。 |
| `Turn` 消息 | 记录有序消息、时间、渠道、内部消息 ID、参与角色（客户、AI、人工）及发送或撤回状态。译文关联对应原文。 |

当前接待收集五个字段 `company`、`cargo`、`quantity`、`origin`、`destination`，对应公司、货物和数量、运输起终点三组信息。每条事实都记录字段、原样摘录、来源渠道、会话 ID 和 `messages.id`，可回查未经翻译的客户原文。未回答的字段用空值，有冲突的回答分别保留候选值和证据，交由员工确认。

人工纠正另存更正值、校对人、时间、理由和证据来源，并关联被更正的事实。交接记录包含实际交接原因、未收集的字段和问询轮数，员工可以沿用已确认的信息。发送状态和交接记录可从 `messages`、`outbox`、`audit` 校验。

## 归档与入库

1. **草稿与修订。** 每个文档保存 `schema_version`、稳定 ID 和递增的修订号。重复处理同一消息只生成一次修订。交接时保留客服接手时的快照，会话继续时更新同一文档。关键来源更正或撤回时，标记受影响事实并重新审核。
2. **审核与脱敏。** 审核公司身份、货物和路线及其来源。电话、证件、详细地址、内部身份和附件按业务权限保留，对知识库使用的文本做脱敏。报价、承诺、临时运力另存为有适用条件和时效的会话记录。
3. **入库与检索。** 由独立审核环节确认可复用内容和可见范围后，才推送已审核版本供检索或导入。索引按文档 ID 更新，随审批撤销、事实更正或原始证据撤回而更新或删除。

后续验收用一条含 AI 接待和人工回复的合成会话，核对事实回查、缺失项、人工纠正、重复导出、撤回后索引更新、报价隔离和脱敏。当前文档定义实施约定，导出、审核发布与知识库索引留待后续实现。
