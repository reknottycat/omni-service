# Telegram 单次扫码接入：操作与验收

## 交付目标

Web K 支持两个界面操作角色，日常运行都不依赖浏览器或 Computer Use：
- **自行设置（无需 Computer Use）**：用户扫官方网页二维码（已登录可跳过），打开配对链接点「开始」，在「设置 → 聊天自动化」保存一次指定 Bot 与回复范围。后台轮询并验证真实连接；不需要用户安装 CLI、提供手机号或办理开发者权限。
- **代操作**：用户扫码；部署者经用户明确授权后，在可持续接手的官方浏览器里代为完成上述点选。没有可用浏览器时不得递交一个只会登录的码并声称已绑定。

没有找到官方公开的网页链接能跳过选择机器人与授权范围并直接完成绑定。`t.me/...?...start` 用来提供账号配对证明，不会替你授予聊天权限。若平台要求额外验证，遵守官方提示。

这条路线是**一次性的官方客户端授权入口**，不是新的运行时，也不是用网页提取用户会话。CLI＋TDLib 仍是一种独立、可选的首次接入方式：部署者已准备自己的官方开发者凭据时才用；不要要求每位账号所有者去申请 API ID/API Hash。开发者后台的手机号和 App 验证码属于另一条流程。

## 本次为什么卡住

| 类别 | 情况 | 处理 |
| --- | --- | --- |
| 平台限制 | Telegram 账号所有者必须确认新会话；开发者后台不能扫码，要求手机号和 App 验证码。 | 首次授权使用官方 Web K，不访问开发者后台。 |
| 界面差异 | 桌面原生界面入口没走通，配对消息收到也不表示机器人已经连接。 | 固定使用 Web K 的「设置 → 聊天自动化」，最终由 Bot API 回执判定。 |
| 操作问题 | 之前把网页登录、机器人连接、开发者注册和每天的消息桥接混在一起。 | 独占一次接入，一次扫码，后续自动运行；不在不同路线之间重复发码、重复配对。 |

2026-11-27 检查 [Web K 官方站点](https://web.telegram.org/k/) 公共资源：线上 `chatAutomation-3E0eprNp.js` 包含聊天自动化界面、回复控制及保存调用；线上 `appBusinessManager-C_JZfGrk.js` 包含 `account.updateConnectedBot` 和 `account.getConnectedBots`。与 [Web K 上游实现](https://github.com/morethanwords/tweb/blob/master/src/lib/appManagers/appBusinessManager.ts) 和 [Telegram 官方协议](https://core.telegram.org/api/bots/connected-business-bots) 一致。**只证明线上端有能力，尚不证明任何实际账号、权限或测试消息成功。** 线上资产名会随发布变化，复验不得硬编码旧文件名。

## 后台与用户自助交接

部署方运行仓库的 `onboarding configure`，**不传 `--telegram-owner` 或 TDLib 参数**，走 Web K／官方客户端分支。首轮测试固定 `--chat-scope allowlist` 和批准的测试私聊 ID，防止网页选择错误范围时误处理别的客户。实例锁和私有配对回执会记住同一 Bot、状态和当前挑战；断开后按相同参数继续，不用再扫登录码或重新配对。后台能证明配对身份与启用/回复回执，不能单靠 Bot API 判断所有聊天范围，网页保存结果仍须核对。

## 一次性部署者操作

1. **发码前全部准备好。** 确认 DGX 实例、飞书应用和管理员、专用 Telegram Bot、预期账号、获准测试私聊及回复范围。用现有实例的私有凭据核对 Bot API `getMe`，不得在终端输出密钥。核实现有机器人和轮询状态；同一个 Bot 只由一个接入者处理，不清队列、不抢活跃消费者、不替换另一机器人。核对同一实例的配对上下文，尚在有效期且匹配时沿用，不因断开换号、重发或重复注册。准备好能够持续接手的受信任浏览器；无法接手则不要发码。
2. **账号所有者只扫码。** 在独立、临时浏览器会话打开 `https://web.telegram.org/k/`，显示官方实时登录二维码，别转发缓存二维码或长期保存图片。账号所有者在已登录的 Telegram App 里使用该账号确认。部署者登录后核对是预期账号；账号不符立即停止，不读取聊天内容。
3. **部署者保存授权。** 不从浏览器提取或注入令牌。若需要配对验证，只由部署者从已登录会话向指定测试 Bot 触发仓库配对链接，账号所有者不操作；已有可核实的同一挑战则沿用。进入 Web K「设置 → 聊天自动化」，选专用 Bot，授权范围仅新私聊或明确获准的测试名单，开启回复，不给删除消息、修改个人资料、星币等额外权限。保存后读取实际配置；保存回执不清楚时先读回，不盲目点第二次。
4. **拿服务器回执。** 从同一专用 Bot 的真实 `business_connection` 事件取得连接 ID，调用 `getBusinessConnection`，核对预期账号、连接已启用且有回复权。在客户端另行核对范围，Bot API 的回复权不证明新旧私聊过滤。配对 `/start`、登录成功、页面显示已选均不能代替这一步。回执未知时保留原接入状态，不用更换 Bot、扫第二次或开启服务来掩盖。
5. **结束临时授权。** 连接确认后登出本次临时 Web K 会话并清理，只处理这个会话，不退出其他设备。后端日常只用已有的 Bot API 令牌和连接 ID，不保存网页登录状态，不需要开放网页。遇到错误时明确暂停并在管理台显示失败；不要偷偷回到 Computer Use。

## 验收：必须关掉网页再测试

- 实例、Bot、账号、连接 ID 一致；`getBusinessConnection` 已读回启用及回复权；浏览器临时会话已结束。
- 启动或重启 DGX 服务，先让获准测试账号给原 Telegram 私聊发一条合成消息。飞书实际收到并产生消息 ID；从飞书发一条获准测试回复，原 Telegram 私聊实际收到并产生消息 ID。
- 验证重复事件不会重复发消息；旧私聊或不在授权范围的聊天没有自动接管。真实客户不参加测试。
- 记录被测版本、目标账号/群的脱敏识别、授权范围、各平台回执、关网页及重启结果。无回执标为「待确认」；不记录二维码、验证码、用户会话、Bot Token 或真实私聊内容。

只验证网页资产或只看到配对消息，不标「已绑定」；只验证已绑定，不标「已收发」。
