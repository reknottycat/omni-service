# P0 · Linux 三渠道模拟验收合同

## 目标与完成边界

在 Linux 上运行可重复验收的客服协议处理服务。Telegram、俄罗斯 MAX 和 WhatsApp 各使用一个官方入口账号，接待相互隔离的多个客户。7 名员工以飞书作为工作端，在客户对应的虚拟共享会话中直接回复；系统识别客户语言并翻译员工消息，同时提供 AI 自动接待、转人工及有准确结果状态的撤回。

**本轮完成标准由用户确定：使用模拟数据在 Linux 上通过即可完成验收。** 真实平台和模型由本地假服务替代；HTTP 入口、适配器、路由、持久队列、数据库与重启恢复必须执行实际代码。这里的“模拟通过”不等于真实账号、真实模型质量或生产环境验证通过。

当前阶段名为 **P0：Linux 三渠道模拟闭环**，已按本合同完成 Linux 模拟验收。后续正式接入另建范围，不回溯增加本轮门禁。

## 已冻结的产品行为

- 渠道是 Telegram、俄罗斯 MAX Messenger、WhatsApp Business Cloud API。名称相近的其他 MAX 产品不在范围内。
- 每个渠道的一个公开账号可以服务多个客户；统一会话键包含渠道、账号及客户/聊天身份，不能只用客户 ID。
- 飞书服务会话的普通员工消息默认发给对应客户。没有“内部消息/对外消息”双模式，也不要求每条消息点发送按钮。
- 只允许当前服务会话的授权成员回复。团队可有 7 人，不要求 7 人同时加入每个客户会话。
- 系统依据客户实际消息识别并记忆会话语言，员工不手选语言。员工消息以客户语言发出，保留员工身份与原文/译文映射。只有问候词、数字等不足以判断语言的输入不能随意覆盖已确定语言。
- AI 可先回答；转人工关键词或不确定结果触发飞书会话创建/绑定。员工介入取消尚未发送的 AI 回复并暂停该会话的新自动回复，明确恢复后才重新启用；已进入网络发送的请求按实际回执处理，无法承诺从客户端消失。
- 一次撤回对应原消息及其实际外发消息映射，返回可区分的结果；平台能力不支持或结果不确定时不显示成功。
- 同一客户在不同渠道的身份默认独立。未经显式核对，不自动合并 Telegram、MAX、WhatsApp 的客户身份。

## 撤回结果的统一含义

| 状态 | 可以告诉员工什么 | 不允许作出的推断 |
|---|---|---|
| `cancelled`（发送前取消） | 系统已取消尚未外发的消息 | 不能据此说已删除客户设备上的内容 |
| `deleted` | 平台删除请求获得明确成功结果 | 不承诺客户没有先看见、截图或通知预览 |
| `unsupported` | 该渠道当前接口不提供这项撤回能力 | 不伪造成功提示或自动发一条“已撤回”代替删除 |
| `failed` | 平台明确拒绝或操作明确失败 | 不把失败隐藏为已完成 |
| `delivery_unknown` / 队列 `unknown` | 请求结果暂时无法确定，需核对 | 不盲重发原消息，不直接标成功或失败 |
